# Detection Engineering

## Detection strategy

This project separates low-confidence atomic detections from higher-confidence correlation alerts.

Atomic rules favor recall. The correlation layer is responsible for precision by requiring multiple distinct behaviors and shared context.

## Atomic building blocks

| ATT&CK | Rule | Type | Severity |
|---|---|---|---|
| T1057 | Windows Process Discovery via Tasklist | KQL | Low |
| T1069.002 | Domain Groups Discovery via Net | KQL | Low |
| T1482 | Domain Trust Discovery via NLTest | KQL | Low |
| T1135 | Network Share Discovery via Net View | KQL | Low |
| T1039 | Remote SMB File Read from Network Share | KQL | Low |
## Why atomic rules are broad

The atomic rules are intentionally broader than final analyst-facing logic. For example, the account/group discovery rule covers both `net.exe` and `net1.exe` and several account/group-related subcommands. This improves recall across Windows implementation differences.

Duplicate atomic signals are acceptable. A single `net` action can produce both `net.exe` and `net1.exe` events, and an SMB file read can generate multiple Event ID 5145 records.

The correlation rule therefore counts distinct behavior families instead of raw alert count.

## Final correlation

Rule name: **Suspicious Discovery and Network Share Collection Chain**

- Type: ES|QL
- Severity: Medium
- Risk score: 60
- Analyst-facing: Yes
- Building block: No
- Validation: PASS

The rule requires at least four distinct behavior families, at least one collection signal, activity across at least two hosts, and at least one source IP in the contributing alerts.
## Correlation logic

The correlation reads Elastic Security alerts generated by the five atomic rules. Each rule name is normalized into a behavior family before aggregation.

Key aggregation fields:

- `behavior_count = COUNT_DISTINCT(behavior_family)`
- `collection_count = SUM(collection_hit)`
- `host_count = COUNT_DISTINCT(host.name)`
- `source_ip_count = COUNT_DISTINCT(source.ip)`
- `latest_signal = MAX(@timestamp)`

The final filter requires:

- `behavior_count >= 4`
- `collection_count >= 1`
- `host_count >= 2`
- `source_ip_count >= 1`
- a recent contributing signal within the freshness window

This prevents duplicate `net.exe`/`net1.exe` or SMB events from being interpreted as separate ATT&CK behaviors.
## Time window and duplicate control

During validation, all six rules were temporarily scheduled every minute to speed testing. After validation they should run on a more production-like cadence.

Recommended correlation settings:
- run every 5 minutes
- look back 15 minutes
- require `latest_signal > NOW() - 5 minutes`

Native alert suppression was not available under the current Elastic license, so duplicate correlation alerts are reduced with a sliding look-back window plus a freshness condition.

## ATT&CK mapping

The final rule maps to:
- TA0007 Discovery: T1057, T1069.002, T1482, T1135
- TA0009 Collection: T1039

## Noise handling principles

Collection filters are kept narrow. Detection exceptions and correlation logic are preferred over broad source-side exclusions whenever the raw telemetry may still be useful for investigation or hunting.
